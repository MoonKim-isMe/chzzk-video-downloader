# DEVELOPMENT_PLAN — v0.2

## Version 0.2 — 동영상 검사 및 복구

### v0.2 제품 목표

v0.2에서는 기존 CHZZK 검색·다운로드 기능을 유지하면서, 로컬에 저장된 동영상 파일의 손상 여부를 검사하고 가능한 범위에서 복구할 수 있는 **동영상 복구** 기능을 추가한다.

사용자는 동영상 파일을 선택한 뒤 빠른 검사 또는 정밀 검사를 실행하고, 검사 결과를 확인한 후 적절한 복구 방법을 실행할 수 있어야 한다.

v0.2 완료 기준:

- 상단 Navigation에 동영상 복구 탭이 추가된다.
- 로컬 동영상 파일을 선택하고 파일 기본 정보를 확인할 수 있다.
- 빠른 검사와 정밀 검사를 각각 독립적으로 실행할 수 있다.
- 검사 결과에서 정상/경고/손상/검사 실패 상태와 복구 가능성을 확인할 수 있다.
- 컨테이너, 영상, 오디오, 타임스탬프, 손상 위치 등 확인 가능한 검사 결과를 사용자 친화적인 형태로 표시한다.
- 빠른 검사 > 복구 흐름을 지원한다.
- 빠른 검사 > 정밀 검사 > 복구 흐름을 지원한다.
- 정밀 검사 > 복구 흐름을 지원한다.
- 복구 시 원본 파일을 덮어쓰지 않고 별도의 복구 결과 파일을 생성한다.
- 가능한 경우 재인코딩 없는 무손실 Remux/타임스탬프 복구를 우선하고, 필요한 경우에만 부분 복구 또는 재인코딩을 사용한다.
- 검사 및 복구 진행률과 취소 상태를 UI에서 확인할 수 있다.
- 복구 완료 후 결과 파일을 다시 검사할 수 있다.

v0.2 기본 범위에서는 존재하지 않는 영상 데이터를 생성하는 복원, DRM 해제, AI 기반 프레임 복원, 전문 포렌식 수준의 바이너리 수동 복구는 포함하지 않는다.

#### Phase 8-A UI 기준

기본 화면 흐름은 다음과 같이 구성한다.

파일 선택 → 검사 방식 선택 → 검사 → 검사 결과 → 복구 → 복구 결과

검사 방식은 사용자가 직접 선택할 수 있으며 빠른 검사를 먼저 강제하지 않는다.

지원해야 하는 대표 흐름:

1. 빠른 검사 → 복구
2. 빠른 검사 → 정밀 검사 → 복구
3. 정밀 검사 → 복구

빠른 검사 결과만으로 복구 방법을 확정하기 어려운 경우에는 정밀 검사를 권장하되, 사용자가 검사 결과를 확인한 상태에서 다음 행동을 직접 선택할 수 있도록 한다.

#### Phase 8-C 빠른 검사 기준

빠른 검사는 전체 영상 프레임을 모두 디코딩하지 않는다.

주 목적은 짧은 시간 안에 다음을 확인하는 것이다.

- 컨테이너가 정상적으로 열리는지
- 영상/오디오 스트림 정보를 읽을 수 있는지
- 재생시간과 인덱스가 비정상적인지
- 대표 지점으로 seek가 가능한지
- 파일 끝부분까지 접근 가능한지
- 명확한 컨테이너/타임스탬프 문제가 있는지
- 정밀 검사가 필요한지

빠른 검사에서 정상으로 판단되더라도 전체 프레임 무결성을 보증하지 않는다.

#### Phase 8-C 구현 메모

- 빠른 검사는 전체 파일을 순차 디코딩하지 않고 ffprobe 메타데이터, ISO BMFF(MP4/M4V/MOV) top-level atom, 시작/중간/끝 대표 구간의 짧은 FFmpeg 디코딩을 조합한다.
- 대표 구간은 영상 길이에 따라 중복되지 않도록 계산하며 각 구간은 기본 2초만 디코딩한다.
- MP4/MOV 계열은 파일 전체를 읽지 않고 atom 크기를 따라 seek하여 `moov` 존재 여부를 확인한다.
- ffprobe에서 영상/오디오 코덱, 해상도, FPS, 채널, 샘플레이트, duration/start time을 수집하여 Phase 8-B 결과 모델에 채운다.
- 대표 구간의 stderr에서 decode/corrupt/timestamp/DTS/PTS 관련 패턴을 분류하고 문제가 있는 대표 구간을 손상 후보 구간으로 기록한다.
- 명확한 timestamp/index 문제는 무손실 Remux 계열을 권장하고, 대표 구간 디코딩 오류가 있으면 부분 복구 가능으로 분류하면서 정밀 검사를 권장한다.
- 빠른 검사 결과에는 `deepInspectionRecommended`와 권장 사유를 포함해 Phase 8-D로 이어져야 하는 조건을 명시적으로 전달한다.
- Phase 8-C에서는 실제 복구 엔진이 아직 없으므로 검사 결과상 복구 가능하더라도 복구 버튼은 실행 불가 상태로 유지한다.
- 빠른 검사 중에는 Wails progress event로 단계와 진행률을 표시하고, 검사 취소 시 실행 중인 command context를 취소한다.
- ffprobe/ffmpeg 원본 진단 출력은 임시 진단 로그 파일로 저장하고 검사 결과에는 경로만 포함한다.
- 빠른 검사 결과가 정상이어도 전체 프레임을 검사한 것이 아님을 UI에 계속 명시한다.

#### Phase 8-D 정밀 검사 기준

정밀 검사는 파일 전체를 순차적으로 읽고 실제 디코딩을 수행한다.

파일 크기보다 영상 코덱, 해상도, 프레임레이트, CPU 성능의 영향을 크게 받는다. 기본 구현은 오류 검출 신뢰성을 우선하며, 하드웨어 디코딩을 사용할 경우 동일한 오류 검출 결과가 유지되는지 별도로 검증한 뒤 적용한다.

#### Phase 8-D 구현 메모

- 정밀 검사는 FFmpeg로 영상/오디오 스트림을 처음부터 끝까지 실제 디코딩하고 출력은 null sink로 폐기한다.
- FFmpeg `-progress pipe:1` 출력을 별도 파이프로 읽어 처리 위치, 전체 대비 진행률, 처리 배속, 경과시간을 Wails event로 전달한다.
- stderr는 전체 내용을 메모리에 누적하지 않고 임시 진단 로그 파일에 streaming 기록하며 메모리에는 오류 집계와 제한된 손상 구간 목록만 유지한다.
- 영상/오디오 decode 오류는 stream index와 주요 codec marker를 함께 사용해 구분하고, 손상 frame/packet 및 PTS/DTS/Non-monotonous DTS/timestamp jump를 유형별로 집계한다.
- 오류 시각은 stderr에 포함된 `pts_time` 또는 `time`을 우선 사용하고, 없는 경우 가장 최근 FFmpeg progress 위치를 사용한다.
- 인접 오류는 같은 유형 기준으로 병합하며 손상 구간 개수를 제한해 장시간 손상 파일에서도 메모리 사용량이 오류 개수에 비례해 계속 증가하지 않도록 한다.
- FFmpeg가 전체 duration 전에 중단된 경우 마지막 progress 위치를 마지막 정상 디코딩 위치로 사용하고 후반부 손상/잘림 후보로 분류한다.
- FFmpeg는 잘린 MP4에서도 exit code 0과 `progress=end`를 반환할 수 있으므로 성공 종료만으로 완주를 판정하지 않는다. 실제 `out_time`과 ffprobe duration 차이가 허용 오차를 넘으면 미완주/잘림으로 판정한다.
- 검사 취소는 기존 공통 검사 context를 통해 FFmpeg process를 종료하고 stdout/stderr pipe가 닫힌 뒤 반환한다.
- Wails 호출은 Promise 기반으로 실행하고 진행 상태는 event로 갱신하여 장시간 검사 중에도 Frontend UI 상태를 유지한다.
- 실제 복구 실행은 Phase 8-E 전이므로 정밀 검사 결과가 복구 가능이어도 복구 버튼은 아직 실행 불가 상태로 유지한다.
- 주요 codec 실파일 검증은 개발 환경의 FFmpeg 7.1.5에서 H.264+AAC, H.265+AAC, AV1+Opus 샘플을 직접 생성하고 Phase 8-D와 동일한 전체 null decode + progress 명령을 실행했다. 세 샘플 모두 `progress=end`까지 완료되고 stderr 오류가 없음을 확인해 V02-8D-11을 완료 처리했다.
- Windows Portable EXE에 포함되는 실제 bundle 조합의 최종 검증은 Phase 8-G의 V02-8G-13에서 별도로 수행한다.

#### Phase 8-E 복구 우선순위

복구는 다음 순서로 가장 보수적인 방법을 우선한다.

1. 복구 불필요
2. Remux
3. Timestamp/Index 정규화 + Remux
4. 손상 데이터 일부 제외 후 정상 데이터 보존
5. 정상 구간까지 부분 복구
6. 재인코딩

원본에 존재하지 않는 프레임이나 오디오를 생성해 원래 영상처럼 복원하는 기능은 제공하지 않는다.

#### Phase 8-E 구현 메모

- 검사 결과는 Backend에서 다시 Repair Plan으로 변환하고, Frontend는 해당 Plan의 전략/예상 처리시간/화질 손실/구간 손실/출력 경로를 실행 전에 표시한다.
- 출력 파일은 기본적으로 원본과 같은 폴더에 `원본명.repaired.확장자`로 만들고 이미 존재하면 `repaired-2`, `repaired-3` 순서로 충돌을 피한다.
- 원본과 출력 경로가 동일한 경우 Backend에서 실행을 거부하며 원본 파일에는 쓰기 작업을 하지 않는다.
- Remux는 stream copy를 사용하고, timestamp 복구는 `genpts + discardcorrupt + avoid_negative_ts`를 적용한 stream copy를 사용한다.
- 부분 복구는 손상 플래그가 있는 packet을 제외하면서 stream copy를 우선하고, 정밀 검사에서 frame/decode 오류가 확인된 경우에는 stream copy로 해결할 수 없으므로 재인코딩 전략으로 승격한다.
- 후반부 잘림은 정밀 검사의 마지막 정상 위치를 기준으로 하되 stream copy가 packet 경계에서 소폭 초과할 수 있으므로 최대 0.5초의 안전 여유를 앞쪽에 둔 `-t` 상한을 사용한다.
- 재인코딩은 최후 순위로 사용하며 MP4/MOV/MKV/TS 계열은 H.264 + AAC, WebM은 VP9 + Opus, AVI는 MPEG-4 + MP3 조합을 사용한다.
- FFmpeg는 같은 디렉터리의 임시 출력 파일에 먼저 기록하고 ffprobe로 파일 크기/스트림 파싱을 검증한 뒤에만 최종 출력 경로로 rename한다.
- 복구 실패/취소/검증 실패 시 임시 파일을 제거하고 기존 원본 및 기존 출력 파일은 변경하지 않는다.
- 최종 확정 시 Windows는 기존 목적 파일이 있으면 실패하는 rename을 사용하고, Unix 계열은 hard-link 생성으로 목적 파일의 원자적 비덮어쓰기를 보장한다.
- 복구 진행률은 FFmpeg progress를 사용해 진행률/배속/경과시간을 UI에 전달한다.
- 복구 완료 후 최종 파일에 빠른 검사를 자동 실행하고 결과를 현재 검사 결과로 표시한다.
- 복구 완료 파일은 현재 선택 파일로 전환되며 `복구 결과 정밀 검사` 버튼으로 즉시 전체 디코딩 재검사를 실행할 수 있다.

- 파일 동일성은 경로뿐 아니라 파일 크기와 수정 시각까지 비교한다. 같은 경로의 파일이 외부에서 교체되거나 변경되면 기존 검사 결과와 Repair Plan을 폐기한다.
- Repair Plan에는 검사 당시 원본 파일 크기/수정 시각을 포함하며 실제 복구 직전 다시 비교해 변경된 파일에 이전 검사 결과를 적용하지 못하게 한다.
- 복구 시작 전 원본 읽기 가능 여부, 출력 폴더 쓰기 가능 여부, 디스크 여유 공간을 검사하고 사용자 친화적인 오류를 반환한다.
- 디스크 공간은 Remux/부분 복구는 예상 출력 크기 + 128MB, 재인코딩은 원본 크기의 약 1.5배 + 256MB를 기준으로 보수적으로 확인한다.
- 앱 종료 시 기존 검사/복구 context 취소를 유지하고, 복구 임시 파일은 Repair 함수의 defer 정리 정책으로 제거한다.
- 검사 완료 파일과 복구 결과 파일은 OS 파일 탐색기에서 해당 파일이 선택된 상태로 열 수 있다.
- Windows에서는 Explorer `/select,`, macOS에서는 `open -R`, 기타 플랫폼은 파일이 있는 폴더를 연다.

#### 예상 처리시간 기준

처리시간은 파일 크기만으로 결정되지 않으며 저장장치 속도, 영상 코덱, 해상도, 프레임레이트, CPU/GPU 성능에 따라 크게 달라진다. 아래 값은 UI 안내와 개발 검증을 위한 대략적인 참고 범위이며 보장 시간이 아니다.

6시간 영상 기준 예상:

- 빠른 검사: 일반적으로 수 초 ~ 1분 내외. 매우 큰 파일, 느린 HDD/USB, 비정상 컨테이너에서는 수 분까지 걸릴 수 있다.
- 정밀 검사 — 1080p H.264 + 일반적인 최신 데스크톱 CPU: 약 30분 ~ 2시간
- 정밀 검사 — 4K HEVC/AV1 또는 디코딩이 무거운 영상: 약 2 ~ 6시간 이상
- 무손실 Remux/Timestamp 복구: 수십 GB 기준 SSD에서 약 5 ~ 30분, HDD/USB에서는 약 15 ~ 60분 이상
- 손상 데이터 일부 제외/부분 복구: 대부분 무손실 Remux와 비슷한 I/O 중심 처리시간을 예상
- 전체 재인코딩 복구: 6시간 영상 기준 약 1.5 ~ 8시간 이상이며, 소프트웨어 H.265/AV1 인코딩이나 고화질 설정에서는 6 ~ 20시간 이상 걸릴 수 있다.

실제 UI에서는 검사/복구 시작 후 처리 속도와 진행률을 이용해 경과시간을 표시하고, 신뢰할 수 있는 경우에만 예상 남은 시간을 제공한다.


#### v0.2 완료 조건

- 동영상 복구 탭에서 파일 선택부터 검사, 결과 확인, 복구까지 하나의 흐름으로 사용할 수 있다.
- 빠른 검사와 정밀 검사가 명확히 구분되며 사용자가 원하는 검사부터 바로 시작할 수 있다.
- 세 가지 요구 시나리오가 모두 동작한다.
- 검사 결과는 사용자 요약과 기술 상세를 함께 제공한다.
- 복구 방법은 검사 결과에 따라 자동 추천되며 무손실 방법을 우선한다.
- 복구가 원본 파일을 덮어쓰거나 변경하지 않는다.
- 대용량 파일에서도 전체 파일을 메모리에 적재하지 않고 streaming 방식으로 처리한다.
- 검사/복구 취소와 앱 종료 시 관련 프로세스 및 임시 파일이 정상 정리된다.
- Windows Portable 환경에서 실제 손상 샘플과 대용량 파일 검증을 완료해야 v0.2 계획 항목을 완료 처리한다.
